## Why mobile FCP/LCP are ~10 s although the server answers in 30 ms

**1. The whole page body is invisible until JavaScript runs.**
The server HTML wraps `<main>` in the `(marketing)/template` animation wrapper:
```html
<main class="flex-grow"><div style="opacity:0;transform:translateY(10px)"> … entire page … </div></main>
```
Nothing inside `<main>` can paint until the JS chunks download, React hydrates, and the entrance animation sets `opacity: 1`. Lighthouse's LCP breakdown (LCP element = the hero `<p>` paragraph):

| LCP phase | Time |
|---|---|
| TTFB | 647 ms (simulated network) |
| Load delay | 0 ms |
| Load time | 0 ms (text, nothing to load) |
| **Render delay** | **10,430 ms** |

Practically all of the LCP is render delay. The prerendered HTML (SSG, edge HIT, 30 ms) is already on the device, but it's hidden. This cancels out the benefit of server rendering.

**2. Render-blocking stylesheets.** Lighthouse estimates **~6.0 s** potential saving on mobile:
- `fonts.googleapis.com/css2?family=Material+Symbols+Outlined:wght,FILL@100..700,0..1` (third-party origin, extra DNS+TLS): 874 ms
- `/_next/static/css/ab1584e3d32cd2d2.css`: 603 ms
- `/_next/static/css/2111bc7b10569bdd.css`

**3. Missing preconnects** to `fonts.gstatic.com`, `google.co.in`, `doubleclick.net`, `analytics.google.com`: ~251 ms.

**4. Unused JavaScript ~93 KB**, mostly `gtag.js` (72 KB unused) and the `/bitelevate` page chunk.

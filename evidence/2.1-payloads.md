# 2.1 / 2.2 API structure, payloads and data handling

The site has no REST/JSON API (see 1.6). It exposes two kinds of backend interface:

1. **RSC (React Server Components) GETs.** `GET <route>` with header `RSC: 1` returns `text/x-component` flight data. The App Router uses these for client-side navigation and prefetching.
2. **Server Actions.** `POST <route>` with header `Next-Action: <id>` and a FormData body. Not invoked (would create records).

Method: regex scans for e-mail addresses, UUID/CUID/ObjectId values, and keys such as `id`, `createdAt`, `updatedAt`, `authorId`, `userId`, `status`, `email`, `phone`, plus storage/DB hostnames (Supabase, Firebase, S3, Cloudinary, Neon, Mongo, Vercel Blob).

## Observations

**No over-fetching. Data stays server-side ✔**
Blog and case-study records only reach the client as *rendered React elements* (`className`, `href`, `children`). No record objects, timestamps, author fields or internal flags are serialized. This is the main data-handling benefit of Server Components over a client-side `fetch('/api/posts')` that returns full rows.

**Persistence layer fingerprint**
IDs used as React `key`s are CUIDs (`cmp6kjrcl00039cex…`, 25 chars, `c` prefix). That is the default of Prisma's `@default(cuid())`, which points to **Prisma ORM over a SQL database**. Blog/diary `lastmod` values in the sitemap (`2026-05-20T09:19:43.825Z … .864Z`, ms apart) show the content was **bulk-seeded** in one script run. The IDs themselves are harmless (public content), but they show the backend stack.

**`/careers` is dynamic but has no DB-backed records**
Its payload contains no DB IDs, so the content looks hard-coded, yet it is rendered per request with `no-store`. Something in the route (e.g. `searchParams`, `cookies()`, `headers()`, or `export const dynamic = 'force-dynamic'`) opts it out of static rendering for no data reason.

**Payload size**
RSC payloads are 30–56 KB per route. Most of that is Tailwind `className` strings that also ship in the HTML. Inherent to the App Router, but it means every prefetch of a dynamic route is a ~50 KB uncached function response.

**Server Action inputs (from 1.6)**
- Client checks: only `required` / `type="email"`. No length caps, no schema, no CAPTCHA.
- `createBitelevateCashfreeOrder` takes no `amount`, so the price is decided server-side ✔.
- `verifyBitelevatePayment(token, orderId)` returns `bitElevateCredentials` (login credentials) in the response body.
- Server-side validation, sanitisation and idempotency **cannot be observed passively**, so they are reported as *Inferred*.

**JSON-LD built from DB content**
`/blog/[slug]` injects `BlogPosting` JSON-LD with `dangerouslySetInnerHTML`, using the post headline/description from the DB. No `<` escaping is present. With current content that's harmless, but a title containing `</script>` would break out of the tag. Next.js docs recommend `JSON.stringify(data).replace(/</g, '\\u003c')`. **Hardening (Low)**.
